## Problem
The server now emits a per-world map `treatment` block (`CartographyTreatmentWire`, shipped in 163-1) and three worlds have raster `map.yaml` content (163-4), but the UI has no renderer for it: a `raster` treatment currently falls through to the generic map cascade, so PD scan maps (Glenross OS-sheet, Années Folles Baedeker, the_circuit highway) never reach the player.

## Technical Approach
Execute plan tasks **12–15** of `docs/superpowers/plans/2026-07-08-mapping-track-a-main-map-treatments.md` (spec: `docs/superpowers/specs/2026-07-08-three-tier-mapping-design.md` §2, §4 A1, §5). The plan is authoritative — it specifies files, interfaces, DOM contracts, and per-task test-first steps:

- **Task 12:** `RasterTreatment` interface + `MapState.treatment?` field in `src/components/MapOverlay.tsx` (type-level; App.tsx already blind-casts MAP_UPDATE payloads).
- **Task 13:** new `src/components/map/RasterMap.tsx` — scan `<img>` + SVG overlay (anchor pins, route lines, current-location marker), pan/zoom lifted from `OrbitalChartView.tsx`, style branches data-driven off `style_hints` (never genre strings). Image load failure → explicit error state, **never** a dag fallback (No Silent Fallbacks, spec §5).
- **Task 14:** `MapWidget.tsx` early-return branch routing `treatment.kind === "raster"` to `RasterMap`; existing dag/orrery/room-graph cascade untouched.
- **Task 15:** GameBoard/MobileTabView reachability wiring test — RasterMap rides the existing dual-registered Map tab; test proves it's reachable end-to-end through the mobile tab path.

## Scope
- In scope: plan tasks 12–15 (sidequest-ui only).
- Out of scope: server/content changes (shipped in 163-1/163-3/163-4), weather zones (163-6), orrery/dag treatment renderers (existing cascade handles them), any Track B changes beyond the data-driven `style_hints` branches Task 13 already specifies.

## Acceptance Criteria
1. `RasterTreatment` is exported from `MapOverlay.tsx` and `MapState` accepts an optional `treatment` field (task 12 type test passes).
2. `RasterMap` renders the scan image (`raster-scan`), one pin per anchored region (`data-region-id`), and marks the current location (`data-current="true"`) inside host `map-panel-raster`.
3. Clicking a pin fires `onNodeSelect(regionId)` — orientation, not travel.
4. Image load failure renders `map-panel-raster-error` explicitly; no silent fallback to dag/generated rendering.
5. `style_hints.faction_layer === "wasteland_defacement"` and `style_hints.routes === "highway_tracing"` alter rendering via data-driven branches keyed off `style_hints`, not genre strings.
6. MapWidget routes `treatment.kind === "raster"` to RasterMap (not MapOverlay); all existing orrery/room-graph/overlay branch tests stay green.
7. Wiring tests: the sanctioned raw-import test proves MapWidget imports RasterMap, and the GameBoard mobile-tab test proves a raster treatment renders `map-panel-raster` when the Map tab is opened (tasks 14–15).
8. `npx eslint` clean on touched files; full `npx vitest run` green in sidequest-ui.
